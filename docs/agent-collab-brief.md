# Agent Collaboration Brief

> 项目：OpenClaw App MVP
> 当前阶段目标：先打通“最小可执行窗口”，优先实现真实 OpenClaw 执行入口。
> 协作模式：主控 + 2 个协作 agent

---

## 0. 你们在做什么

这是一个 **OpenClaw App 的 MVP** 项目。
目标不是一次把产品做完整，而是先跑通一个最小闭环：

1. 用户创建任务
2. 后端入队
3. worker 消费任务
4. sandbox 真正调用 OpenClaw 执行
5. 结果/状态能正确落回系统

当前已经有：

- FastAPI 后端骨架
- PostgreSQL 数据模型
- Redis 队列占位
- Docker sandbox 生命周期管理
- worker 雏形
- sandbox runner stub

当前最优先事项：

- **把 placeholder 的 sandbox runner 替换成真实 OpenClaw 执行入口**

暂不优先：

- 前端界面
- 流式输出
- 复杂商业化/计费细节
- 重型架构（K8s / 多机编排）

---

## 1. 组织结构

### 主控（我）

我是主控 / 集成负责人。我的职责：

- 维护整体技术方向
- 拆任务、控优先级、避免跑偏
- 审阅你们产出的方案和改动
- 做最终集成与验收
- 维护长期记忆、项目上下文与关键决策

### 你们（两个协作 agent）

你们不是各自独立乱做，而是：

- 在各自明确边界内推进
- 把关键发现、阻塞、接口假设讲清楚
- 尽量产出“可集成”的结果，而不是只给想法

---

## 2. Agent 角色定义

## Agent A：OpenClaw 执行链路专员（最高优先级）

### 你的任务

你只盯一件最关键的事：

**把 sandbox 里的占位执行器，替换成真实的 OpenClaw 执行入口。**

### 你需要回答的问题

1. 当前项目里，sandbox / worker / task 的执行链路是怎么串起来的？
2. 真实 OpenClaw 应该如何在 sandbox 内被调用？
3. 用户 message 应该如何传给 OpenClaw？
4. OpenClaw 的执行结果应如何被 runner 捕获？
5. 失败、超时、异常退出时，runner 该输出什么供 worker 判断？
6. 在不做流式输出的前提下，最小闭环怎么落地最稳？

### 你的交付物

优先交付下面这些：

- 一份简明执行链路说明
- 对 `sandbox/runner.py` 的可运行改造方案
- 如果需要，对 sandbox Dockerfile / worker 调用方式提出最小改动
- 明确输入/输出约定：
  - 输入从哪里读
  - 输出写到哪里
  - 成功/失败状态怎么表达
- 尽量给出可落地代码，而不是只给思路

### 你的边界

你**不用**负责：

- 认证系统
- 前端
- 计费 UI
- 大规模架构扩容

如果你发现这些问题，也只需要：

- 简短记录
- 不要被它们带跑

### 你的原则

- 优先最小可执行，不追求第一版优雅
- 不要为了“未来可能的完美形态”阻塞当前闭环
- 如果 OpenClaw 官方 CLI / 运行方式有限制，优先找最稳的兼容方案

---

## Agent B：后端工程加固专员

### 你的任务

你负责把外围工程链路补得更扎实，让 Agent A 的执行入口能更容易接进来。

### 你重点关注

1. `task -> worker -> sandbox -> task状态回写` 这条链路是否完整
2. 当前 task 状态更新是否足够清晰
3. 超时、失败、重试、异常日志是否有最小闭环
4. sandbox 状态与 task 状态是否容易出现不一致
5. 哪些地方需要小重构，才能更稳地接真实执行器

### 你的交付物

优先交付：

- 当前后端执行链路的问题清单（短、准）
- 最小必要的工程修正建议
- 若合适，直接给代码修改：
  - task 状态流转更清楚
  - worker 超时/失败处理更明确
  - sandbox service / docker service 的接口更清晰
- 明确告诉主控：
  - 哪些改动是“必须现在做”
  - 哪些可以延后

### 你的边界

你**不要**主导：

- OpenClaw CLI 研究
- runner 的核心执行实现
- 前端或产品层大改

如果你碰到执行入口相关问题：

- 标出来
- 和 Agent A 对齐接口
- 不要抢对方主线

### 你的原则

- 先保链路可靠，再谈设计漂亮
- 只做能明显降低集成难度的改动
- 避免大面积重构

## 3. 共同协作规则

### 规则 1：都要围绕“最小可执行窗口”

当前不是做“最终产品”，而是做：

- 真执行
- 有结果
- 能落状态
- 失败可判断

### 规则 2：优先产出接口约定

如果你需要和另一个 agent 协作，请优先把这些讲清楚：

- 输入文件/参数格式
- 输出文件/结果格式
- 成功/失败/超时标记
- 依赖哪个模块先准备好

不要模糊地说“这里之后再接”。

### 规则 3：发现阻塞，先缩小问题

不要一句“这个做不了”。
要改成：

- 卡在哪一层
- 当前证据是什么
- 最小替代方案是什么
- 是否值得绕过

### 规则 4：不要抢主控决策

你们可以提出强建议，但不要各自改变项目主线。
涉及这些内容时，要交由主控拍板：

- 是否改技术路线
- 是否引入新组件
- 是否扩大当前开发范围

### 规则 5：文档要短而能执行

不要写长篇空话。优先写：

- 结论
- 依据
- 建议改动
- 风险
- 下一步

## 4. 当前统一技术口径

这是你们默认遵守的技术方向：

- 后端：FastAPI
- 数据层：PostgreSQL + Redis
- 模型网关：LiteLLM
- 执行层：Docker sandbox
- 当前阶段：10-20 人 MVP
- 当前主目标：真实 OpenClaw 执行入口
- 当前非主目标：流式输出、前端完善、复杂计费、分布式扩容

如果你想偏离这些方向，需要先给出充分理由，并交主控判断。

## 6. 你们分别最该产出的第一份反馈

### Agent A 第一条反馈应该长这样

- 当前真实执行入口最可能接在哪
- runner 现在是怎么跑的
- 要换成真实 OpenClaw，最少要改哪几个文件
- 最大风险是什么
- 我建议先用哪种方式落地

### Agent B 第一条反馈应该长这样

- 当前 task/worker/sandbox 链路的主要薄弱点
- 哪 2-4 个改动最值得现在就做
- 哪些状态字段/错误处理不够用
- 哪些问题先别碰

---

## 7. 最后的要求

你们的目标不是“表现自己很聪明”，而是：

**帮主控更快拿到一个能跑的最小闭环。**

如果你不确定，就优先选择：

- 更小的改动
- 更清晰的接口
- 更容易验证的方案
- 更少的隐含依赖

先把 OpenClaw 真正跑起来。其他都可以后补。
